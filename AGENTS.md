# CodeDen: agent guide

CodeDen is a local-first harness for coding agents. **`docs/DESIGN.md` is the locked design and the source of truth.** Read the relevant sections before changing behaviour; anything in its "Locked decisions" table needs a design discussion first.

## Layout

```
apps/
  server/     Hono server: security, SQLite event log + projections (Drizzle), UI WebSocket, RunnerClient
  runner/     Runner process: provider sessions, event journal, lock file, WebSocket protocol server
  web/        React 19 + Vite SPA (Tailwind v4, shadcn/ui, TanStack Router + Query, Zustand)
  cli/        The published `codeden` package: CLI entry, bundles server + runner + web with tsdown
  desktop/    The desktop app (Electron): main process, preload bridge, server host, electron-builder packaging
packages/
  contracts/  zod schemas for everything that crosses a boundary (events, entities, protocols, settings)
  providers/  ProviderAdapter / ProviderSession interfaces, the Fake provider, the Claude Code, Codex and OpenCode adapters, a generic ACP client and the Cursor and Gemini CLI adapters on it
docs/DESIGN.md
changes/      Changelog fragments: one file per user-facing change, assembled into CHANGELOG.md at release
scripts/release/  bump-version.mjs (the Release workflow's version bump) and changes.mjs (fragments)
scripts/harden/   CodeHarden's own: release.sh, publish.sh (npm-release.mjs), setup-fork.sh, fork-config.sh (which upstream, branches and package), sync-cooldown.sh (the 48-hour rule for upstream changes; sync-cooldown-report.sh shows it on pull requests, sync-cooldown-release.sh asks it for a release, sync-waiver.sh checks the owner's waiver), the build-time version and channel defines, upstream-drift.test.mjs (the guard against upstream's identity coming back), brand/ (the logo's one SVG source and the script that makes every icon from it), dev-preview/ (this repository's own dev command for a dev preview: `run.mjs` takes the web and server ports from `WEB_PORT` and `API_PORT` and keeps its home in `.codeden-dev/preview/`; `docs/dev-preview.md`)
```

Key entry points:
- Contracts: `packages/contracts/src/` (agent events `agent-events.ts`, items `items.ts`, runner protocol `runner/`, UI WebSocket `ws.ts`, persisted events `events.ts`, work/conflicts `work.ts`, factory `factory.ts`).
- Server: `apps/server/src/server.ts` (`startServer({ port, dataDir, token })`), dev entry `src/dev.ts`.
- Runner: `apps/runner/src/runner.ts` (`startRunner`), process entry `src/main.ts`.
- Web shell: `apps/web/src/components/shell/`.
- CLI: `apps/cli/src/cli.ts`.
- Desktop: `apps/desktop/src/main/main.ts` (entry), `desktop-app.ts` (wiring), `src/server/host.ts` (server child), `src/preload/preload.ts` (`window.codedenDesktop`); the UI side is `apps/web/src/lib/platform-desktop.ts`. User guide: `docs/desktop.md`.

Node 24+ and pnpm 10 (`corepack enable`).

Don't use `--ignore-conflicts`, which writes a merge snapshot with two parents. To repair a fork that already reached `main`, change only the newer snapshots (their `prevIds`, and add the other branch's entities to `ddl`), never a shipped `migration.sql`, then check that `pnpm db:generate` reports no changes and `pnpm --filter @codeden/server exec drizzle-kit check` passes |

## Conventions

- **Contracts first.** Any new message, event, entity or setting is added to `packages/contracts` (with JSDoc and a round-trip test) before it is used. Validate at boundaries with the shared schemas.
- **Plain TypeScript**, strict, ESM. **No Effect**, no clever abstractions; mainstream patterns that other agents can follow.
- **Small modules:** keep files under ~400 lines; split by concern.
- **Honest capabilities:** UI and orchestration read `ProviderCapabilities`, never branch on a provider id.
- **Heavy UI code loads on demand.** Pages are lazy routes, and the terminal, diff viewer and code editor come from `apps/web/src/components/on-demand.tsx`; never import those libraries statically from anything the web app's entry reaches. `apps/web/test/entry-chunk.test.ts` checks it. See `apps/web/README.md`.
- **Events are append-only.** Projections are written in the same transaction as their event (`apps/server/src/events/`), so they can be rebuilt from the log.
- **Security:** server and runner bind 127.0.0.1 only; every request needs the install token; never log or persist tokens in transcripts.
- **Tests: keep them lean.** The bar is that the app installs and works; CI checks exactly that (typecheck, lint, `pnpm test`, build, the packed CLI installed and started). Add a Vitest unit test (next to the package in `test/`) when logic is easy to get wrong and costly when wrong: the risk classifier and other security checks, contracts round-trips, migrations, parsers, anything that can lose data. Don't add end-to-end, real-browser or real-process tests for a feature unless asked, and keep `pnpm test` fast and deterministic (no real timers or races; use the Fake provider, never live agent turns). Bugs users hit get an issue and a fix, with a regression test when the logic warrants one.
- **Process-heavy suites get room for a busy machine.** `startHarness` (`apps/server/test/support/harness.ts`), and `startServer` without `runner: false`, start a real runner process with the Fake provider, plus git worktrees. `vitest.config.ts` finds those server files by reading them and runs them as the `@codeden/server (runner)` project, beside the runner's worktree suites (`@codeden/runner (worktrees)`, a list in the config), with 120 s test and hook timeouts (and no lower ones in the files). The harness's `waitUntil` waits 60 s, and its server gives runner commands at least 90 s (`runnerRequestTimeoutFloorMs`), so the product's own 5-30 s deadlines don't fire first. They stay in `pnpm test` and CI, in the shared pool: a worker limit of their own would need a phase of their own after the fast suites (Vitest 5), which made the run 40-50% slower. Instead, when the machine is already busy at start (under half idle), the config runs a quarter of the CPUs' worth of workers for every project. The other runner, server and release-script suites get 40 s, the web suites 15 s. Reach for the harness only when the test is about the server and the runner together (sessions, turns, worktrees, MCP over a live runner). For server logic, prefer services over a real SQLite database with a scripted `RunnerPort` (`support/factory-env.ts`, `support/github-env.ts`) or `startServer({ runner: false })`; those stay in the fast pool. Wait on the condition with `waitUntil` and a generous deadline, never a fixed sleep or a tight timer. `node scripts/test-under-load.mjs` runs three `pnpm test` at once, as parallel factory builds do, to check for timing flakes.
- **Tests don't depend on the time of day.** The factory test env (`apps/server/test/support/factory-env.ts`) runs the process clock from a fixed instant (`TEST_START` in `support/test-clock.ts`, mid-morning local time), so a test can move it hours ahead without crossing midnight into the daily digest, counters and budget; a test about day boundaries starts near midnight on purpose (`createFactoryEnv({ startAt })`). Elsewhere, pin the clock (`vi.setSystemTime`) instead of building on the real `Date.now()` when a test moves time by hours. `CODEDEN_TEST_CLOCK=23:50` starts the server suites' system clock at that local time, and `pnpm test` runs a sample of the factory, budget and digest suites at 23:50 and 00:05 (`@codeden/server (clock …)`).
- **Agent sessions don't inherit CodeDen's internal `CODEDEN_*` variables** (its home, its installer and the like; `packages/providers/test/agent-env.test.ts` keeps it so), and the root `vitest.config.ts` drops them for every worker as well. Run the tests as they are: there's no need to look for those variables first.
- **Never mention other harnesses or products as inspiration** anywhere: code, comments, docs, commits. Describe CodeDen on its own terms.
- **Commits:** conventional commits (`feat(server): ...`, `fix(runner): ...`, `chore: ...`), one logical change per commit. `pnpm typecheck && pnpm lint && pnpm test` must pass; the first two are checked before a push and all three in CI (see "Checks before a push and in CI").
- **Changelog notes are fragments.** A user-facing change adds its note as its own file, `changes/<issue>-<slug>.md` (front matter `section: added | changed | deprecated | removed | fixed | security`, then `- ` bullets in the style of `CHANGELOG.md`). Never edit `CHANGELOG.md` for unreleased work, so pull requests never conflict on it. Docs-only and internal changes need no note. Format: `changes/README.md`; `pnpm test` checks it.
- **Dev preview is a person's feature.** `apps/server/src/services/dev-preview/` runs a project's dev command in a session's worktree (`docs/dev-preview.md`). The command comes only from `<home>/dev-preview.json`, which only `PUT /api/dev-preview/projects/:id` writes (this computer only, with `confirm: true`). Never read a command from the repository, never add it to `Project` or to a request that starts a preview, and never add an agent or MCP tool that sets it or starts one. Secure Foundation only offers values that fill the settings form (`secureFoundationDevPreview`, from the names it kept in `<home>/secure-foundation.json`): it never writes `dev-preview.json`, no Secure Foundation route takes a command, and a name goes into an offered command only when it is a plain name (`isPlainDopplerName`). The switch at the top of a thread is there for every project and off until a person switches it on (`pmEnabled` defaults to off); in a project with nothing stored it offers the app's own suggestion through the settings' own confirmation dialog (`apps/web/src/components/harden/dev-preview/setup.tsx`, `confirm-dialog.tsx`), and nothing else in the UI may call `confirmProject`. Every start goes through `starter.ts`, which reads the stored settings itself; the PM thread's preview follows only the base branch recorded at confirmation (`Project.defaultBranch` is agent-writable). A preview's processes are ended only through `process-table.ts` (`familyOf`): never signal a process by an id alone, and never a process group as a whole. The suites with real processes are in `pnpm test:slow` (`test/dev-preview-process.test.ts`); the ones with real git run in the server's process-heavy project.
- **Secure Foundation lists repository secrets; it never handles one.** `apps/server/src/services/secure-foundation/repo-secrets/` reads a project's workflow files as text (no YAML loading, nothing of the project run, never through a link) for the `secrets.NAME` and `vars.NAME` they use, and asks GitHub which exist with two fixed commands that request names only (`gh secret list|variable list --repo <owner>/<repo> --json name`). Never add a route, form field, agent tool or command that sets a secret or variable, takes a value, or puts one on a command line; never request, log or store a value or `gh`'s output. Checking is for this computer only (`POST …/repository-secrets/check`); another device reads the last result. Steps for a known name live in `SECURE_FOUNDATION_KNOWN_REPO_SECRETS` (`packages/contracts/src/secure-foundation-repo-secrets.ts`) and name the page they come from; a name and a repository reach a shown command only through `repoSecretName` and `repoSecretsRepository` (`docs/secure-foundation.md`, "Repository secrets the project's workflows need").
- **What Secure Foundation requires is written once.** `packages/contracts/src/secure-foundation-requirements.ts` lists the local tools and the accounts (`SECURE_FOUNDATION_TOOLS`, `SECURE_FOUNDATION_ACCOUNTS`). The requirements page, the services Go's sign-in checks ask (`secureFoundationServices`), the install hint of a missing tool and the Node.js version in the setup brief all read it: add or change a requirement there, never in one of its readers. Its check (`apps/server/src/services/secure-foundation/requirements.ts`, `GET …/requirements`, this computer only) reuses the sign-in checks and answers found or not, a version number and signed in or not, nothing else: no account name and no command output (`docs/secure-foundation.md`, "Requirements"). Clerk is in the list as `neededFor: "later"`: the page asks Clerk's own CLI whether it is signed in, but the install needs no Clerk account, so it must stay out of Go's checks (`secureFoundationServices`), out of the setup brief and out of what brings the page up; the email `clerk whoami` prints is never passed on.
- Generated files: `apps/server/drizzle/` (migrations, via drizzle-kit) and `apps/web/src/components/ui/` (shadcn). Add shadcn components with `pnpm dlx shadcn@latest add <name>` from `apps/web`.

## Checks before a push and in CI

- **CI runs the tests.** `pnpm test` runs in CI for every pull request into `harden` that is ready for review, a sync pull request (`sync/*`) included; the review of a sync relies on that result. It does not run for a draft (it runs when the draft is marked ready), for a pull request into another branch, or for a push, including the push that a merge into `harden` makes: what reaches `harden` was tested on its pull request. Typecheck, lint, the build, the self-update check and the packed install run on every event, as before. A documentation-only pull request skips all of it; one that changes the root `README.md` does not, because the drift guard reads that file. A newer push to a pull request cancels its older run. The **CI result** check fails when the tests should have run and didn't.
- **The pre-push hook is light.** `scripts/harden/hooks/pre-push` runs `pnpm typecheck` and `pnpm lint` (`scripts/harden/push-checks.sh`) and refuses the push when one fails. It never runs the tests. A pass is remembered for that exact tree, so an unchanged commit pushes at once. It is enabled per clone, once (worktrees share it): `git config core.hooksPath scripts/harden/hooks`. Not checked: tags, pushes to `harden`, `main` and (in a fork of CodeHarden) `mirror`, sync branches (`sync/…`), branches that change documentation only, and a branch that isn't the checked-out commit. `git push --no-verify` skips the hook; don't use it to get around a failure, and say so in the pull request if you ever use it.
- **Don't run the whole suite for every push.** While you work, run the tests of what you touched (below). `scripts/harden/local-checks.sh` runs all of `pnpm test` on the checked-out commit and remembers a pass; it is a manual command for when you want the whole suite here, and nothing calls it.
- **Targeted tests.** One package: `pnpm exec vitest run --project @codeden/contracts` (the names are in `vitest.config.ts`; the server and the runner have several projects, so `--project '@codeden/server*'`). One file: add its path inside the package, `pnpm exec vitest run --project '@codeden/server*' test/factory-policy.test.ts`. The fork's script tests, the drift guard included: `pnpm exec vitest run --project scripts harden/`.

## One request, one pull request

- **One request = one branch = one pull request, opened once, as the last step.** No "part 1 of 3" pull requests unless the owner asked for staged delivery, and no follow-up pull request for something that belonged in the first.
- **Ready to open** means all of this is true before the pull request exists:
  - the whole request is implemented: code, tests, docs, changelog fragment, drift-guard entries;
  - `pnpm typecheck` and `pnpm lint` pass locally;
  - the tests of the touched packages pass locally (targeted, not the whole suite; CI runs the whole suite on the pull request);
  - you have re-read your own full diff against `harden`;
  - the description says what was verified, what wasn't, and the known limits;
  - nothing is left as "will follow".
- **Push the branch once, when it is ready**, not as a backup during the work. Commits stay local until then.
- **After opening**, push to an open pull request only to answer a review finding or a CI failure, batched into one push, never a stream of small ones.
- **Releases:** at most one release per merged pull request, cut only after the merge and green CI. When several pull requests serve one request, release once, after the last. The reminder that the tag isn't on npm goes with the release report.
- **Something new while the work is in flight** goes on the same branch before the pull request opens, or becomes a new request after this one merges. Say which.

## Releasing

CodeHarden has its own releases; upstream's Release workflow (`.github/workflows/release.yml`) is disabled here and stays disabled. The app's own version (`apps/cli/package.json`, `apps/desktop/package.json`, `SOURCE_VERSION`) stays upstream's and is never bumped here; `scripts/release/` is upstream's and unused.

1. **A release** is one commit on `harden`, `release: <version> (upstream <sha>)`, tagged `v<version>`. The version is `YYYY.MMDD.HHMM`, the release time in America/New_York (`2026.0105.0518`). `scripts/harden/release.sh` makes it: it writes `VERSION`, a new entry on top of `CODEHARDEN-CHANGELOG.md` (`## <version> — YYYY-MM-DD HH:MM`, then `### upstream (<UPSTREAM_REPO>)` and `### <this repository's name>` with the non-merge commit subjects since the last release; here `leonvanzyl/codeden` and `codeharden`) and `state/upstream-base` (the upstream commit `harden` now contains). `--dry-run` prints what it would write; `--push` pushes the commit and the tag in one atomic push. It fails if the tag exists and never forces anything. Where the last release was is not read from the working tree: it is the newest release tag `origin` has whose commit is on `harden`'s own line, and the upstream base that release wrote; the script refuses when `VERSION` or `state/upstream-base` were changed since. Before every release it asks GitHub about what was merged since the last one and refuses when upstream commits among it had not waited out their cooldown ("The sync cooldown" below), so it needs `gh` on PATH, signed in, every time.
2. **Who runs it.** The "Upstream sync merge" workflow, after it merges a sync pull request, and a maintainer after merging our own changes (`scripts/harden/release.sh --push` on an up-to-date `harden`). After a sync was merged by hand, the release goes through only when that sync had waited its 48 hours, or the owner waived it.
3. **npm** is published by hand, by the owner, for the releases they choose: `scripts/harden/publish.sh` on a clean checkout of the release tag. The package is the repository variable `PACKAGE_NAME` and its command is that name without the scope (here `codeharden` for both); its npm version is the CodeHarden version with leading zeros stripped per field (`2026.105.518`). The rename happens in a staging copy at pack time; `apps/cli/package.json` keeps upstream's name and version. No tokens, no Trusted Publishing, no publish from CI. An agent runs the real publish only when the owner asks for that release to be published in the conversation: it runs the publish step under a pseudo-terminal, opens the approval URL npm prints, and the owner approves in the browser (the `npm-release` skill has the steps). An agent signs in to npm only as part of such a publish and only when npm is signed out, with the web sign-in and the same technique (`node scripts/harden/npm-release.mjs login`: it passes the owner the URL npm prints and they approve in their browser), and never handles a password, token or one-time code. Steps: `docs/codeharden-npm-release.md`.
4. **Desktop installers** are built and attached by the "Desktop installers" workflow (`.github/workflows/harden-desktop.yml`), which a person dispatches for an existing release tag: first with `dry-run` on (builds on Windows, macOS and Linux, keeps the installers as workflow artifacts, touches no release), then with it off (creates the tag's GitHub release as a draft, attaches the installers and the update files, then publishes it as the latest). It never runs by itself. An agent dispatches the real run only when the owner asks for that release's installers. A real run waits for the owner's approval: its macOS and Windows jobs use the GitHub environment `release` (required reviewers, only the `harden` branch), which holds the signing secrets, and the publishing job needs those jobs; a dry run uses no environment and is given no secret, so it is always unsigned. The approval is the owner's alone: an agent never approves, rejects or bypasses a review (not in the browser and not through the API or `gh`), never creates or changes the environment and never handles its secrets, which the owner enters in the environment's settings. Each system's job gets only its own secrets; a real run must sign the systems in the repository variable `SIGNED_INSTALLERS` (`macos` when unset) and stops without their secrets; the packaged app carries the CodeHarden version in its npm form and its own identity (`CodeHarden`, `com.codeharden.app`, home `~/.codeharden`), all from `packages/contracts/src/harden-channel.ts` and `scripts/harden/channel-define.mjs`. Packing installers is a release, a dry run and a local `pnpm desktop:dist` included: `apps/desktop/scripts/package.mjs` sets `HARDEN_RELEASE_PACK=1` for every run without `--dir`, and the channel is then read strictly, so a fork without `PACKAGE_NAME` is refused instead of warned (`pnpm desktop:build`, `pnpm desktop:dev` and the tests only warn). Steps: `docs/codeharden-desktop-release.md`.
5. **Nothing above is a fixed name.** Which upstream is followed, on which branch, and the npm package come from the repository variables `UPSTREAM_REPO`, `UPSTREAM_BRANCH` and `PACKAGE_NAME` (optionally `HARDEN_BRANCH` and `MIRROR_BRANCH` for the working and mirror branches); the release repository is the repository itself. `scripts/harden/fork-config.sh` resolves them for the shell scripts, the "config" job for the sync workflow and `scripts/harden/channel-define.mjs` for the build; CodeHarden's values (`leonvanzyl/codeden`, `main`, `codeharden`, `harden`, `main`) are the defaults in `harperaa/codeharden` only. Anywhere else the scripts and the workflow refuse until the variables are set. `scripts/harden/setup-fork.sh` sets a fork up (README, "Make your own hardened fork").

## The sync cooldown

Upstream changes reach users only after they were approved and then waited 48 hours. One rule decides it, `scripts/harden/sync-cooldown.sh`: the label `sync-approved` applied at least 48 hours ago (its last `labeled` event in the pull request's timeline), no push to the head branch since, and no `sync-hold`. Three things ask it and none has a copy of its own: the pull request's status "Sync cooldown" (the "Sync cooldown report" workflow, every hour and on label changes), the sync workflow's merge job, and `scripts/harden/release.sh`, which asks about everything that was merged since the last release, at the moment it was merged. `docs/codeharden-sync-cooldown.md` has all of it.

- **For the sync reviews: the "Sync cooldown" status is a clock, not a CI check.** It is expected to be unfinished (pending, or failing after a push) until 48 hours after `sync-approved` was applied. A reviewer never counts it as a failed or unfinished check, never waits for it, and never tries to turn it green; every other check on the head commit must still have finished and passed. A `sync/...` pull request has no such status before it is approved; it appears with the approval ("Cooling down until ...").
- **It applies to every pull request that brings upstream commits**, whatever its branch is called. A sync lands through its own `sync/...` pull request, with a merge commit. Never squash or rebase one, and don't merge a sync branch into another branch to land it: the release asks about that pull request just the same.
- **Never merge a pull request whose "Sync cooldown" status is not green.** Pending, failing, or missing on a pull request that brings upstream commits (a sync that is not approved has none, and a new head has none until it is approved again). Not with the merge button, not with `gh pr merge`, not with `--admin`, not by pushing the merge yourself. This holds for a sync labelled `sync-needs-review` too: a person merges that one, after its 48 hours.
- **Never waive.** The only way around the cooldown is the "Waive sync cooldown" workflow, and it is the owner's. An agent starts it only when the owner asks for that waiver in the conversation, with the three values a refused release prints (the upstream commit, the pull request, the commit). An agent never approves, rejects or bypasses its review (not in the browser, not through the API, not with `gh`), never creates or changes the environment `sync-waiver` or the variable `SYNC_WAIVER_APPROVERS`, and never deletes a waiver run. The approval is the owner's alone.
- **A refused release is reported, not worked around.** When `release.sh` refuses because of the cooldown, or because it could not be decided, stop and report its message to whoever asked for the release. Don't write the release commit or the tag by hand, don't change the scripts or `COOLDOWN_HOURS`, don't edit `VERSION`, `state/upstream-base` or the changelog, don't re-label the merged pull request, and don't publish an earlier or a hand-made tag instead. Waiting does not help either: what counts is the moment of the merge.
- **What an agent never sets.** `release.sh` is run as it is. Never pass it `--upstream-ref`, and never set `UPSTREAM_URL`, `UPSTREAM_REPO`, `UPSTREAM_BRANCH`, `SYNC_COOLDOWN_NOW`, `SYNC_COOLDOWN_REPO`, `SYNC_WAIVER_APPROVERS` or `RELEASE_NOW` for it or for the cooldown scripts: they say what upstream is, what time it is, which repository is asked and who may waive. They exist for the tests and for a fork's own configuration.
- **What is enforced and what is not.** The automatic merge and the release script are enforced by code that reads GitHub's own records. A merge by hand is not blocked by GitHub, the release script runs on this machine, upstream code copied in by hand (a cherry-pick, a patch) leaves nothing the script can see, and sessions here act with the owner's GitHub sign-in, which GitHub's API would let approve a waiver. So the rules above are instructions, and the waiver is a deliberate, recorded step, not a cryptographic separation.
- **Changing the rule** is a change to `scripts/harden/` and to the two workflows `sync-cooldown.yml` and `sync-waiver.yml`, all protected paths for syncs, as are the three files a release writes (`VERSION`, `CODEHARDEN-CHANGELOG.md`, `state/`). The hours, the labels and the waiver's names are written once, in `sync-cooldown.sh`; the tests (`scripts/harden/sync-cooldown.test.mjs`, `sync-waiver.test.mjs`, `release.test.mjs`, `sync-workflow.test.mjs`) hold the workflows to them. The tests use a stub `gh` (`test-support/stub-gh-cooldown.sh`) and need `jq`, which GitHub's runners and macOS have.

## The logo, the wordmark and the icons

CodeHarden's mark is a halved shield in one red and white; the name beside it is written `Code` + `Harden`, the second part in the red.

- **One source:** `scripts/harden/brand/mark.svg` holds the shape and both colours. `node scripts/harden/brand/make.mjs` writes everything else from it and is safe to run twice (it needs Playwright's Chromium to draw the PNGs): the mark and colours for the UI (`packages/contracts/src/harden-mark.ts`), the colour tokens (`apps/web/src/harden-brand.css`; the dark theme's lighter red for the word is computed to reach 4.5:1), the web icons (`apps/web/public/harden/`), the app icon as `.icns`, `.ico` and PNGs (`apps/desktop/build/harden/`) and the tray, menu-bar and window icons (`apps/desktop/assets/harden/`). To change the design, edit the SVG, run the script and commit; `node scripts/harden/brand/contact-sheet.mjs <out.png>` draws a preview of all of it first. `pnpm test` fails when the committed text files don't match the SVG.
- **Upstream's images are never overwritten** (`apps/web/public/favicon.svg`, `public/icons/`, `apps/desktop/build/icon.png`, `apps/desktop/assets/*.png`): a binary file both sides changed can't be merged. The fork's files are new ones, and the code points at them: the `Logo` and `Wordmark` components (`apps/web/src/components/shell/`), the icon paths in `apps/desktop/electron-builder.config.mjs` and `desktop-app.ts`, and the web build, which rewrites the icon links of `index.html` and the manifest's icons (`scripts/harden/web-identity.mjs`; it fails when upstream adds an icon the fork has none for). Each is a `CALL_SITES` entry of the drift guard.
- **The wordmark is for the name as a brand** (the sidebar, Settings › About, the setup, sign-in and locked screens, the server's own "locked" and "not built" pages). The split is `hardenWordmark` (`packages/contracts/src/harden-brand.ts`): a product whose name doesn't start with `Code` is written whole. Ordinary sentences that say CodeDen stay as they are.
- The macOS menu-bar icon is a template image (one colour, the system tints it); the amber "waiting" dot on the tab icon and the Windows taskbar is a status colour, not the logo, and is upstream's.

## Keeping the fork's changes through upstream merges

Upstream arrives in `harden` by merge, every day. The fork changed about 130 of upstream's files, mostly one-line call sites that read the install's identity and update channel from `packages/contracts/src/harden-channel.ts` and `harden-version.ts` instead of upstream's fixed values.

- **What git does.** A line the fork changed that upstream changes too is a conflict, and a conflict is reviewed. Everything else merges silently.
- **What git does not catch.** A conflict resolved to upstream's side, which drops the fork's call site; and new upstream code that names upstream's values in a new place (the `codeden` npm package, `leonvanzyl/codeden`, `~/.codeden`, `codeden-projects`, port 4317, `dev.codeden.app`, `codeden://`, the `codeden` keychain service, the app name `CodeDen`). Either makes part of the product behave like upstream again: updating from upstream's package, writing into upstream's home, colliding with the upstream app.
- **The guard** is `scripts/harden/upstream-drift.test.mjs`, part of `pnpm test` (so of CI's test step on every pull request into `harden`, a sync included). It reads the tracked product source as text (`apps/*/src`, `packages/*/src`, the build and packaging configs and scripts; not tests or docs) and fails when (1) an upstream identity value is used as a value outside its `ALLOWED` list, (2) a file in its `CALL_SITES` list no longer reads the fork symbol it must, or is gone, or (3) `README.md` lost the credit on top or names upstream below it outside its `README_ALLOWED` list. The message names the file and line, what came back and which fork constant to use.
- **When it fails on a sync**, fix the code on the sync branch: read the fork's constant in the new place, or put the dropped call site back (for a moved file, re-apply the change where the logic went and update the entry's path). Don't quiet it. `.codeden/VISION.md` is the fork's own text in a file upstream ships too: a conflict on it is resolved to the fork's text, and the guard fails when its first line is upstream's again. `README.md` is the same kind of file, and upstream edits its own often: README conflicts resolve to the fork's wording; carry upstream's content changes over by hand (CodeHarden where the text means this product, with the fork's command, home, port and links). The credit on top keeps naming CodeDen and says the README is derived and adapted from the CodeDen repository; a mention below it that really is upstream gets a `README_ALLOWED` entry with its reason.
- **An `ALLOWED` entry needs a reason** a reviewer can judge: the value is not the install's identity there (a workspace package name, a protocol or stored id, the `codeden` MCP server name, `.codeden/` inside a repository, brand text left on purpose). "The test failed" is not a reason. Keep its pattern as narrow as the text it excuses; an entry that matches nothing any more fails the test and is removed. When upstream moves an allowed line to another file, the entry is widened on `harden` first, in a pull request of its own (it names the old and the new path, and one match in either keeps it used), and narrowed back to the new path after the sync has merged. It is never fixed inside the sync's merge commit. A new redirected call site gets a `CALL_SITES` entry in the same pull request.
- **What it cannot catch.** It matches text, not behaviour: a value assembled from parts (`"code" + "den"`), read from a file or the environment, or reached through an upstream constant with a new name passes. So does upstream's own name where the list has no rule: other machine-wide names (a temp folder, a Docker image tag, a new settings key), a new default that isn't one of the values above, and behaviour upstream changes inside code the fork never touched. Comments are skipped, and so are tests and docs. The review of a sync still reads the diff; this test is a net under it.
